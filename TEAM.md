- The user sends every request through the lead, and the lead hands out the work.
- Before closing a session, the lead checks that it's idle and has no unfinished request.
- **Resume fast after a usage limit (the user's rule, 2026-10-16).** The account's usage limit stops the lead and every helper at once. The lead keeps a REPEATING hourly check-in (create_trigger with a cron, e.g. trig_01NKBjg2UJa1tXFjWU5Zd29L), never only a one-shot reminder (a one-shot that fires while blocked is lost: that cost 2.5 hours on 2026-10-16). Each check-in resumes stopped workers, nudges stalled helpers, and carries on.
- **Handover before auto-summarizing (the user's rule, 2026-10-16).** The user prefers our handover method to the automatic summary. Every session (lead and helpers) warns early when its memory is getting full, or when the next task looks big enough to fill it: helpers tell the lead, and the lead tells the user in plain words. Don't wait for the automatic summary. **When (the user's rule, 2026-10-16 evening):** helpers hand over at about **70% of memory** (about 700k of 1,000,000). The lead is different: before each bigger step (a new combined build, a check-in, a new pillar or plan), it checks how much memory it has left and whether that step fits; if it doesn't, it hands over first, so a step never starts that can't be finished. Then write a handover brief for a fresh session in our usual style (role, branch, build numbers, current state, open work, the user's decisions, how to test) and keep TEAM.md current, so the new session starts clean. **Refresh before handing over (the user's rule, 2026-10-17):** a handover note written in advance must be brought up to date right before the actual handover (latest hashes, what's in flight, new decisions), never handed over stale.
