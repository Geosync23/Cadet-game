# Performance for 0.99.6: why it gets worse the longer you play (PF1)

PF1, the performance seat for 0.99.6, for lead 49. Branch `claude/perf-0996`, made from `claude/integration` 0.99.5
(6475bb30, game sha256 93aed54f...5164). Started 2026-11-01.

The user's report: "Take a good look at performance for the next update too. It gets worse the longer I play. If it
means some sacrifice to visuals then show me an example and I may approve."

## The short answer

1. **Nothing inside the game piles up.** Over 40 ship days of play (skipping the nights, an hour on two decks each day)
   and over 12 ship hours of unbroken real-time play, the game's own work per frame, its worst frames, deck changes,
   the night skip, memory, the number of things in the scene, the page, timers, listeners and the sound all stay flat.
   A save from Day 40 loaded into a fresh page runs at the same speed as a fresh game skipped to Day 40. The save
   stays small (largest 131 KB by Day 280; the budget is 250 KB).
2. **So the slowdown the user feels is most likely the phone itself warming up.** The game draws a full picture on
   every screen refresh, never resting: up to 2 device pixels per CSS pixel, with edge smoothing (antialiasing) and a
   2048 soft shadow map drawn every frame. On a 120 Hz screen like the TriFold's that is 120 full pictures a second.
   After some minutes a phone slows its graphics chip to stay cool, and the game gets choppier the longer you play.
   This can't be measured in our headless test browser (it has no real graphics chip). **One reading from the phone
   would settle it** (below).
3. **Separately, I found stalls that come with the calendar** (not with play time): single frames of 40-386 ms on a
   desktop (perhaps 4-5 times that on a phone) when the crew's day is planned again in one go, and every ship hour
   during the diplomatic visit. One of them is fixed here with the same answers (`shipEffectsAt`, below); the rest are
   proposals for their owners.
4. **Visual trade-offs, all off:** four switches with before/after pictures in `plans/perf-0996-visuals/`, for the
   user to judge. The one most likely to help a phone that gets slower as it warms is the frame cap (no change to the
   picture itself).

## How I measured

All on 0.99.5 (93aed54f), Playwright and the container's Chromium, three.js r128 served locally, a 390x844 window. The
scripts are in the scratch folder of this session and summarised here so they can be redone (I will copy them to
`plans/perf-0996-probes/` with the fixes).

- **The fixed scene:** each sample stands you in the middle of the mess hall at 10:00, zoom 1.5, and lets the crew
  settle 90 frames. Game code per frame: perf_check's measure (the best of three batches of 20 frames, drawing
  skipped). A drawn frame: the same with drawing (SwiftShader, so only for comparing like with like).
- **The long run (40 ship days):** each day skip to 07:30 (as after a night's sleep), play an hour of frames on two
  decks in turn (all seven decks over the week), then the fixed scene. Sampled every day: game code, worst frames
  (every frame of a whole ship hour timed one by one), draw calls, JS heap after a full garbage collection (exact, from
  the browser's debugger; Chrome's own figure is rounded), geometries, textures, scene objects, page elements, sim
  timers, listeners and live timeouts (hooked), the save (made the way `saveGame` makes it, with its time, its write
  to storage and its read back), each saved record's size, and every top-level table's size (count and JSON length,
  3,280 names) on days 1, 2, 5, 10, ... 40.
- **The real-time stretch:** Monday 07:00 to 19:00 without a skip, in the mess, sampled every ship hour, then a fresh
  page at the same moment.
- **Whole days frame by frame:** Days 13-19 in real time without a skip, every frame over 25 ms recorded with the time
  spent in the main loop's ticks and the planner.
- **Reload:** the Day 40 save loaded into a fresh page, against a fresh game skipped to Day 40, same scene, twice.
- **Heap snapshots** on Day 5 and Day 40 (grouped by kind of object).
- **Sound:** off in every check (it never starts under automation). A separate run with the real clock and `?sound`
  for 20 real minutes, counting every audio node made, playing and finished.
- **The save to Day 280:** `player_check.py --long 280` (the save budget check).

## What it probably is, and the one reading that would tell

The game asks a lot of the graphics chip every frame, and never lets it rest:

- `renderer.setPixelRatio(Math.min(devicePixelRatio, 2))` (section 1, line 422): on the TriFold (pixel ratio about 2.6
  folded, 2.0 open) every frame is drawn at 2 device pixels per CSS pixel: about 3.4 million pixels open.
- `antialias: true` (line 421): edge smoothing, several samples a pixel.
- A 2048 x 2048 soft (PCF soft) shadow map drawn every frame (sections 1 and 5).
- The main loop asks for the next frame straight away (`requestAnimationFrame(loop)`, section 12), so it draws at the
  screen's own rate: 120 a second on a 120 Hz screen, even when nothing on screen moves.

A phone running its graphics chip flat out heats up, and after some minutes it slows the chip (and the processor)
to cool down. Then the same work takes longer and the frames come further apart: "it gets worse the longer I play".
Restarting the game doesn't help, a rest does.

**To confirm it on the user's phone (5 minutes of their time, nothing installed):** open the game with the Dev link
(`#dev` on the game's link), Dev panel, the Speed tab, in a busy place (the mess at dinner). Screenshot the card when
you start, and again after 30-45 minutes of play in the same sort of place. If "Frames ... a second" drops while
"Game code a frame" stays about the same, it's the graphics chip slowing down as it warms. If game code a frame goes
up too, something in the game is growing after all, and the card's numbers tell me where to look.

## Fixes in this branch (the same picture, the same answers)

### F1. `shipEffectsAt` keeps its answers across machine changes (section 17, the systems engineer's: for their review)

`shipEffectsAt(deck, t)` caches `fxFrom(deck, record)` by deck and hour, but drops the whole cache whenever `MACH_REV`
changes, and `MACH_REV` goes up for nearly everything (a job taken, a part used, every machine hour). `fxFrom` reads
only the deck, the hour's record (`MACH_HIST.get(h)`, a new object each time `machRecord` writes one) and fixed tables
(`machineList()`, `MACHINE_FX`, `MACHINE_KINDS`, `MACH_BRANCH`, `SYSTEMS`). So the effects are now also kept on the
record itself (`FX_OF`, a WeakMap from the record to its effects by deck). A record that is rewritten is a new object,
so it is worked out afresh; dropped records are freed with it. The per-revision map and everything callers see is
unchanged.

- **Same answers:** every 7th call checked against a fresh `fxFrom` over Days 2-30 (skips, an hour on a deck each day)
  and a further real-time day: 0 differences in about 29,000 checked answers (202,751 calls, most during the visit).
- **Gain, Day 18 (the visit), every frame over 10 ms in 16 ship hours of real-time play:** before, 15 of 16 hours, 15-49 ms
  (`socCourtesy` 12-41 ms); after, 4 hours, 17-24 ms (`socCourtesy` 4-10 ms).
- **Checks:** see "Test results" below.

### Tried and dropped

- Working out each guest room-mate's warmth once per hour in `socCourtesy` (section 20): no gain, the guests weren't
  sharing rooms; the cost was each call's, which F1 fixes. Not kept.

### Not reproduced: backlog 14 and 18d (perf_check's "memory grows across deck round trips", +2 geometries)

On 0.99.5 four laps of every deck give 470, 470, 470, 470 geometries and 41 textures. On lap 4 two crowd props were
packed for the first time (`_propPacks` 0 to 2, someone picked something up): a first use, not a leak. That is the likely
+2 seen before. Suggest closing both, or a tolerance of a few geometries in perf_check's rule.

## Visual trade-offs for the user (all off; nothing changes unless the user says yes)

Pictures: `plans/perf-0996-visuals/`. For each of three busy scenes (Sunday dinner in the mess with 67 crew, the
Captain's address in the auditorium with 48, quiz night in the bow lounge with 55; 390x844 on a 3x screen like the
user's phone), `<scene>-<option>.jpg` puts a 1:1 piece of today's picture beside the same piece with the option, and
`<scene>-<option>-small.jpg` / `<scene>-today-small.jpg` are the whole screens at phone size.

"Drawing work" is the time to draw one frame in the test browser's software graphics (SwiftShader) with the picture
waited for, the median of 7. It stands in for the graphics chip's work, to compare options; it is not a phone's time.

| Option (switch, preview) | What changes on screen | Drawing work: dinner / address / lounge | My view |
|---|---|---|---|
| **Frame cap 60** (`PF_CAP_ON`, `#pfcap`; `#pfcap-30` for 30) | Nothing in a still picture. On a 120 Hz screen, movement updates 60 times a second instead of 120 (most games run at 60 or 30) | Half the frames on a 120 Hz screen: half the work and heat a second (checked: 600 of 1,200 frames in 10 s; ship time the same). No change on a 60 Hz screen | **Recommended first**: the most likely help for "worse the longer I play", and it doesn't change how anything looks |
| **Sharpness 1.5** (`PF_PR_ON`, `#pfpr`) | Drawn at 1.5 device pixels per CSS pixel instead of 2 (44% fewer pixels): very slightly softer edges and text on the ship; the HUD, cards and Mail are page text and stay sharp | -22% / -26% / -33%; unfolded -28% / -41% / -35%; folded -23% / -23% / -32% | Recommended second: hard to see at arm's length |
| **No edge smoothing** (`#pfaa`) | Stair-steps on slanted edges: lamp shades, rails, sofas, table edges | -30% / -34% / -33% here, but phone chips smooth edges far more cheaply than software graphics, so the real gain is likely much smaller | Not recommended: the most visible, the least sure gain |
| **Shadow map 1024** (`PF_SH_ON`, `#pfsh`) | Shadow edges a little softer and blockier | -5% / -6% / -1% | Small gain; only with the others |
| Sharpness 1.5 + shadow map 1024 together (`#pfpr.pfsh`) | as both | -24% / -30% / -33% | |

Also measured and not offered: plain (not soft) shadows saved 0-2%.

The previews work on the playable link (the hash, as `#evvessel` did): `#pfcap`, `#pfpr`, `#pfsh`, `#pfaa`, joined with a dot
for several (`#pfcap.pfpr`). The user could try `#pfcap.pfpr` on the phone for a session and see whether it still slows
down. If the user picks some, switching them on for everyone is its own reviewed step (one line each).
