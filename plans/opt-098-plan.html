What I found, in short

1. The busiest scenes spend most of their time preparing the picture, not running the game. At Sunday dinner in the mess, zoomed out, the game's own work (the crew, the clock, the galley) takes 2.7 ms a frame. Then three.js, the drawing library, spends another 6.5 ms getting 638 drawing jobs ready for the graphics chip. Our speed check (perf_check) never sees that second part, because it skips drawing to save time.

2. Two things cause a quarter to a third of those drawing jobs, and both can be cut. You and up to 3 crew standing near you are each drawn as 16 separate pieces, twice (once for the picture, once for the shadows): about 128 jobs. The furniture is merged by material, and many materials differ only in colour: on Deck 3, 182 materials become 65 if colour is kept on the shape instead.

3. Opening the game: about half of the start-up wait is preparing the graphics chip's programs (shaders) for the first picture. One switch saves 0.25-0.3 s of it here, in all 3 paired runs, with identical pixels.

4. Memory is fine. It stays flat over two tours of every deck. No work planned there.

The baseline (0.96.0)

Measured in a cloud test browser (4 cores, software drawing) with nothing else running. A phone runs the game's code roughly 4 to 5 times slower than this machine, so a 6 ms cost here is roughly 25-30 ms on a mid-range phone, against a 16.7 ms budget for smooth 60 frames a second. The drawing itself (the graphics chip's part) can't be timed in a software browser, so it's counted in drawing jobs instead. Phone portrait, zoomed out (0.7), the busiest view.

The changes, ranked

Gains are estimates from the measurements above until each is built and proved. Open a row for the details.

1You and the crew near you drawn as one piece each, not 16about 120 fewer drawing jobs at dinner (a fifth)medium riskquestion 1

What: the crowd is already drawn as one shape per 12 people, with their joints moved by the graphics chip. You, and the up to 3 story crew who get a full body when they're within about 4 tiles, are still 16 pieces each (head, arms, legs and so on), each drawn twice. The same baked shapes would become one shape per person, moved the same way the crowd's are.

Gain: Sunday dinner from 638 drawing jobs to about 515; three.js's preparing time about 1-1.5 ms less here (roughly 4-6 ms on a phone), in every scene where someone is near you.

Risk: the pieces' positions get worked out on the graphics chip instead of before it. The sums are the same, but rounding can land differently, so a few edge pixels may come out one shade apart. Your uniform's tint, props in your hands, and the rank pips all have to carry over; the builder checks each.

Proof: cadet_test against the build before; close-up shots of you and a full-body crew member standing, sitting, walking, carrying, at the four phone sizes; a difference picture if any pixel moves (question 1); the paired timing below.

2Furniture that differs only in colour drawn togetherabout 80-90 fewer drawing jobs at dinnermedium riskquestion 1

What: after a deck is built, its furniture is merged into one shape per material. Many materials differ only in colour (182 on Deck 3, 65 if colour is ignored; 106 to 49 on Deck 4). Keeping each piece's colour on its own corners lets those share one shape. Only solid materials take part; see-through ones stay as they are.

Gain: the mess's 142 furniture jobs fall to about 55; less on quieter decks. Together with item 1, Sunday dinner zoomed out goes from 418 picture jobs to roughly 270, well under the 450 budget, which leaves room for new events in the mess.

Risk: the colour is the same number either way, but it reaches each pixel by a slightly different route, so a rare pixel may come out one shade apart. Furniture would also be drawn in a different order, which doesn't change solid things (no two surfaces share a plane, by the phone rules).

Proof: cadet_test; every deck at the four phone sizes, day and night; the paired timing.

3Stop checking each shader for errors while you playset aside 28 October: no real gain when measured in alternating order

What: three.js stops after preparing each graphics program to ask whether it had errors, which makes the browser wait for each one in turn. One switch turns that off (renderer.debug.checkShaderErrors). It stays on in Dev mode and in the checks, so a broken shader would still be caught.

Gain: first picture 2.72-2.97 s instead of 3.03-3.24 s here (3 of 3 alternating runs faster). On a phone the programs can be prepared side by side, so the saving should be larger; the Dev Speed card will show it on your phone.

Proof: pixels identical by design (nothing about the picture changes); cadet_test; devmode_check for the Dev mode side.

4The rest of the still furniture casts shadows the cheap wayset aside 28 October: about 10 safe draws, about 0.1 ms

What: since 0.27 most still things cast their shadow through a few plain stand-in shapes. About 20 merged furniture shapes in the mess, and some event decorations added after a deck is built, still cast their own. They'd join the stand-ins.

Gain: small but steady: fewer shadow jobs in every room.

Proof: the same triangles cast the same shadows (the rule the stand-ins already follow); cadet_test; shots of each changed room with shadows on.

5Battery: no more than 60 pictures a second, and an optional saver settingset aside: your answer, 28 October (no cap, no saver)

What: the game draws a new picture every time the screen refreshes. Many phones, foldables included, refresh 120 times a second, so in a calm room the game draws twice as many pictures as a 60 Hz phone for the same movement. A cap at 60 keeps every picture the same, just fewer of them. Separately, a "battery saver" in the device's settings (off unless you turn it on) could draw at a slightly lower sharpness and with softer shadows: that one changes the look, so only when chosen.

Gain: can't be measured in our test browser (it has no real screen); your phone's Dev Speed card would show frames a second before and after.

Proof: with the cap, every picture is identical (cadet_test steps frames itself, so it's untouched); with the saver off, the game is identical.

Measured and set aside

  • Adding the texture speckle in one batch at start-up: the same pixels (checked, all 17 textures), but no time saved (6 alternating runs: 5.2-5.9 s against 5.3-5.8 s). Making the speckle faster any other way changes the look (decided 21 October).
  • Lighter crowd posing and smaller crowd uploads: measured in the first optimization pass at under 0.2 ms a frame; still true.
  • Planning the crew's day later at start-up (about 0.35 s here): it would bend the rule that a day's plan comes out the same whenever it's made.
  • Instanced things set up again every frame (about 450 extra graphics calls a frame at dinner): a habit of three.js itself, which we load as it is; not worth patching.

How each gain is proved, through the noise

Run-to-run timing moves by 1-2 ms, more than some of these changes. So each change is proved with the old and new builds open side by side in one quiet browser, in the same scene, measured in turns (old, new, old, new... 15 times). The result is the typical difference between each pair and how many pairs went each way, not two separate runs. The drawing-job counts are exact and need no repeats. The timing now includes three.js preparing the picture, not only the game code. The measuring scripts are in plans/opt098-probes/.
