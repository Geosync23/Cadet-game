Optimization Pass Plan

The pass you asked for right after the ship-wide events: a faster page load, a lighter game for phones, and checks that finish sooner. Measured on build 0.64.7 (claude/integration 6ea5acf) before anything is changed. Nothing here has been built yet; your answers at the bottom decide the details.

The goal, in plain words

  • The game should open faster and run smoother on your phone, and the checks we run before every change should take less time, so the team gets more done each night.
  • Nothing you see or play changes. Every change has to leave the game exactly as it is: the same pictures to the pixel, the same crew going to the same places at the same minutes, the same saves. If a change can't prove that, it doesn't go in. (The game picks its "random" choices from a fixed list of numbers. If code that runs while the game opens used up one of those numbers, every later choice would shift, so these changes never touch that list.)
  • The checks still play the real game, with drawing on. No "skip the drawing" shortcuts (your rule). We only stop them doing work twice or doing work they don't need.

At a glance

  • Opening the page takes about 7 seconds in our test machine on 0.64.4, 0.64.5 and 0.64.7 alike. The jump to 16-18 seconds seen last night happened because several checks were running on the same machine at once. The game itself didn't get slower.
  • Three things cost the most when the game opens: painting the "grain" noise into every texture (1.0 s here, roughly 4 s on a mid-range phone), building the first deck (1.3 s), and preparing the 3D shaders for the first picture (about 3.5 s here, but much less on a real phone's graphics chip).
  • One hidden cost stands out: when the crowd changes (someone sits, stands or picks up a tray), the game re-sends a big block of crowd shape data to the graphics chip, sometimes 4 MB in one frame. On a phone that's a small hitch. In the checks it's 74% of day_check's time on a busy deck.
  • The busiest frame (Sunday dinner in the mess, 69 people) spends 2-3 ms of game code before drawing here, so about 8-14 ms on a mid phone, out of the 16.7 ms a smooth frame allows. Half of it is posing the crowd.
  • Running every check once takes about 2 hours (nearly 3 at a release), and player_check alone is a third of that. Most turns change one area but run far more checks than that area needs.
  • 14 changes are proposed (items 0-13), ranked by how much they help against how risky they are, built over a setup turn and 3 turns by 3 builders and a reviewer, merged by the build master.

3The crowd sends less to the graphics chip: parked (measured, not worth it)section 8b · render seat · parked 2026-10-21 by lead 23 on RN1's numbers
gain: none for the checks, under ~1 ms on phonesrisk: low

Parked, not built (2026-10-21). RN1 measured it again in turn 1 and the gain wasn't there:

  • Nothing is sent twice. The "15.6 MB a frame, more than the whole crowd" came from the probe counting each call's whole source array; three r128 on WebGL2 sends only the changed stretch. The true numbers for day_check, Deck 3, Day 1: 115 MB over the day, at most 8.4 MB in one drawn frame (after an hour of skipped frames nearly everyone has changed, so most of the group really is new).
  • day_check's time isn't uploads. In this test browser gl.finish() returns at once, so the software renderer's queued drawing (600-900 ms a frame) is billed to the next call that has to wait, usually the crowd's upload. With a real wait after each frame (reading back one pixel), the whole day's uploads take 30 ms and the new buffers 0.3 s, against 15.6 s and 11 s without it. day_check's time is drawing its ~50 frames.
  • In play it's small. Sunday dinner, standing in the mess hall (70 people, 600 drawn frames, phone portrait): 31 KB a frame typically (p95 31 KB), at most 1.69 MB (the 4.4 MB was the same miscount). On a phone that's around a millisecond.

Fixed places would have changed the crowd's buffer layout (a new proof, risk in section 8b) to save about a millisecond in a rare frame. Kept on record here; probes: plans/opt-probes/buf_true.py, buf_play_true.py. The original proposal follows.

The original proposal (revision 2)
gain: medium on phones; checks: measured in turn 1risk: low

What happens now: the crowd is drawn in groups of 12 people. When one person in a group changes (sits, stands, picks up a tray), the game rewrites everything from that person to the end of the group and re-sends it. In three.js r128 each piece of shape data can send only one stretch a frame, from the first change to the last. In play that's 31 KB a typical frame, with spikes up to 4.4 MB. In day_check, up to 15.6 MB goes out in one drawn frame after an hour of skipped frames. That's more than the whole crowd's data (about 6 MB in the mess), so some of it is sent more than once.

How it's built (the chosen way): first, turn 1 finds out why some data goes twice; if that's a plain waste, fixing it alone may give most of the check gain. Then fixed places: each person gets a fixed stretch of the group's data, big enough for their largest shape, and the unused end of each stretch holds empty triangles that draw nothing. One person changing rewrites only their stretch, and the single upload runs from the first changed stretch to the last. Sending several separate stretches would need a hook into three's internals (renderer.attributes), so it's left out unless turn 1's numbers say it's worth it. Smaller groups are ruled out: they cost draw calls, and the mess hall is at 418 of 450.

Gain (estimate): in play, one person changing sends about a twelfth of a group instead of up to all of it, so the 4.4 MB spikes become a few hundred KB at most. After a long skip most people have changed, so the checks gain mainly from the "sent twice" fix; turn 1 measures that before anything else is built.

Why it's safe: the same triangles in the same order, with empty ones in between, so the same picture. The layout changes, so the proof doesn't compare what's sent. After every drawn frame of a ship day on every deck, it compares the triangles the group draws (read back from the buffers, empty ones skipped) with the old build's, then the picture: cadet_test ALL IDENTICAL, and 32 crowd shots after skipped frames (the test that caught the last bug of this kind, in 0.27.28).

4Keep compiled shaders across deck changessections 4c, 12 · render seat
gain: medium (deck changes; measured)risk: low

Built (RN1, 2026-10-21, claude/opt-render): keepShaders() in section 1, called once after each render. Measured again with a real wait after each frame: laps 2-3 of all seven decks, first frames 10.6-10.9 s kept against 11.1-12.4 s plain; programs stop at 22 after one lap at both phone sizes; cadet_test and every deck's shot at 390×844 and 844×390 identical. The 9.2 → 6.3 s below was partly drawing time billed to later frames (see item 3).

What: three.js throws a shader away when the last thing using it is unloaded, so every deck change compiles shaders again, even on a deck you've just left. Keeping each compiled shader once it exists costs a little memory (the game uses about 22) and nothing else. Measured with a probe (plans/opt-probes/keep_probe.py): over a second lap of all seven decks, the first frames after the changes took 6.3 s instead of 9.2 s. Decks 5, 1, 6 and the rec deck dropped from 0.5-2 s to 10-30 ms. On a phone each saved compile is tens to hundreds of milliseconds of hitch when you arrive.

Also measured, and not worth it alone: warming the shaders with renderer.compile(scene, camera) right after a deck is built doesn't save time. The first frame falls from 1-2 s to about 40 ms, but the compile itself takes 0.7-2.4 s (compile_probe.py). It only moves the wait inside the deck change's fade, which may still be nicer on a phone; the seat tries it with the keeping above and keeps it only if your phone's numbers (item 8) say so.

Why it's safe: the shaders are the same ones, so the pictures are too. cadet_test ALL IDENTICAL, deck_check OK, and memory over deck round trips still flat. The hook into three's internals (holding one extra use of each compiled shader) is named in one place with a comment, and the probe checks that the shader count stops growing after one lap. Decks with their own lights or fog can need their own shader versions, so the build review counts the shaders after every deck at both phone sizes, and the memory over deck round trips must stay flat (ER2's note).

6Paint texture grain faster, same pixelssection 2 · game-code seat
gain: medium (at most about half of the 1.0 s here, ~2 s on a phone)risk: low

Built in part (RN1, 2026-10-21, claude/opt-render): the grain loop, with the same pixels and the same random numbers, saves about 25 ms here: the loop was 26 ms of the "1.0 s". The rest (735 ms) is the browser reading each texture back from the graphics chip. The only way round that, drawing the textures on the CPU, would open the page 1.8 s sooner here but changes the pixels of 101 of 106 textures. Parked: the user said don't change the look of the game. Numbers: plans/opt-measure.md "Faster texture painting".

What: the grain painter adds a random speck to every pixel of every texture, one by one (8 textures, all while the game opens). The same specks, in the same order, can be made with a much tighter loop, with no change to the numbers drawn. "Half" is the most we expect, not a promise: each speck still needs its own random number.

Why it's safe: a probe fingerprints every painted texture and the game's random-number position after opening; both must match the old build exactly. Then cadet_test ALL IDENTICAL.

7Lighter busy framessections 8b, 10, 14, 11, 15, 19 · game-code seat

Parked: measured, small (RN1, 2026-10-21; lead 24 agreed). The three pieces below would save at most about 0.15-0.2 ms, across four or five owners' sections. A phone already runs this frame in about 10-12 ms of the 16.7 ms a smooth frame allows. Numbers: plans/opt-measure.md "Lighter busy frames".

What: small, separate savings, one area at a time:

  • The screen-size answers and the HUD's button positions (matchMedia, getBoundingClientRect) are remembered instead of measured every frame. They're forgotten whenever the screen changes size or turns, and whenever the HUD itself changes: the needs strip, the device opening or closing, a button appearing.
  • "Where should this person be now?" (whereIs, planWhere, walkGap) is asked once per person per ship moment instead of several times a frame.
  • The crowd's posing work is trimmed.

The rule these answers follow (the crew's planner never reads records built while the game runs): the remembered answers are used only by the frame code, never by the planner. Each is labelled with everything it was worked out from, and all are forgotten on anything that can change a plan or a place within the same ship moment: a time skip or sleep, a reload, joining a tradition, a meeting, an event's phase changing, a Dev mode jump.

Why it's safe:

  • The crew: after 900 frames of Sunday dinner with zoom changes, every crew member's position, pose and goal, the save and the random-number position must match the old build exactly (the method used for 0.27.27). A new probe does the same through each "forget" case (a Dev jump, a time skip, joining a tradition), person by person. day_check's output is identical line for line.
  • The HUD: interactions_check and bubble_check pass at 390 and 360 wide. They test where taps land and where bubbles sit, which pictures can't.

Each owner reviews their area.

9Remember painted textures between visitssections 2, 4b · game-code seat
gain: medium (every open after the first)risk: mediumquestion 2

What: after the first open, keep the finished textures in the browser's storage (IndexedDB, which holds several MB; the 5 MB save storage is too small). Each is labelled with the build number and a fingerprint of the painting code. Later opens load them instead of painting (about 1 s here, several on a phone). It also stores where the random-number list stood after painting, so everything after it carries on exactly the same.

Never inside the checks: with ?nosave (every check) the game never reads or writes the cache, so every check still paints. A wrongly labelled cache is ignored and repainted. If the storage is full, blocked or slow, the game simply paints, as now.

Why it's safe: one probe opens the game on purpose with the cache, and once without it. Both must give the same pixels, and the same random-number position after opening and after visiting every deck. So both ways are tested, not just the painting one.

Risk: a wrongly labelled cache would show old textures; that's what the fingerprint guards against. Planned after the safer items.

Not proposed

  • Checks without drawing: your rule. Our test browser has no window on screen (that's what "headless" means), but it still draws the game exactly as the checks always have, and that stays.
  • Visible trade-offs (softer or blockier shadows on small screens, people far away moving less often, fewer decorations): each would change what you see. Only if you ask for it (question 6).
  • Test browsers keeping compiled shaders between runs: tried (a kept browser profile and Chrome's shader store): no measurable gain, the software renderer compiles them again anyway. (Keeping them within one run is item 4, and that does help.)
  • Fewer kinds of materials to compile fewer shaders: it would change colours and shine.
  • Cutting the dialogue file down: it's already stored in the fast form and takes under 0.1 s to read. Most hosts send the page compressed (1.6 MB instead of 5.5 MB); the lead checks that the playable link does.

How each change is proven to change nothing

  • Pictures: cadet_test against the build before, ALL IDENTICAL (the known one-level renderer noise excepted), plus the item's own extra shots.

  • The random numbers: the "random" list's position after opening and after a played hour is compared with the old build. Shared kit made at load still never draws from it.
