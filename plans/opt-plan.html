Optimization Pass Plan

The pass you asked for right after the ship-wide events: a faster page load, a lighter game for phones, and checks that finish sooner. Measured on build 0.64.7 (claude/integration 6ea5acf) before anything is changed. Nothing here has been built yet; your answers at the bottom decide the details.

The goal, in plain words

  • The game should open faster and run smoother on your phone, and the checks we run before every change should take less time, so the team gets more done each night.
  • Nothing you see or play changes. Every change has to leave the game exactly as it is: the same pictures to the pixel, the same crew going to the same places at the same minutes, the same saves. If a change can't prove that, it doesn't go in. (The game picks its "random" choices from a fixed list of numbers. If code that runs while the game opens used up one of those numbers, every later choice would shift, so these changes never touch that list.)
  • The checks still play the real game, with drawing on. No "skip the drawing" shortcuts (your rule). We only stop them doing work twice or doing work they don't need.

At a glance

  • Opening the page takes about 7 seconds in our test machine on 0.64.4, 0.64.5 and 0.64.7 alike. The jump to 16-18 seconds seen last night happened because several checks were running on the same machine at once. The game itself didn't get slower.
  • Three things cost the most when the game opens: painting the "grain" noise into every texture (1.0 s here, roughly 4 s on a mid-range phone), building the first deck (1.3 s), and preparing the 3D shaders for the first picture (about 3.5 s here, but much less on a real phone's graphics chip).
  • One hidden cost stands out: when the crowd changes (someone sits, stands or picks up a tray), the game re-sends a big block of crowd shape data to the graphics chip, sometimes 4 MB in one frame. On a phone that's a small hitch. In the checks it's 74% of day_check's time on a busy deck.
  • The busiest frame (Sunday dinner, 72 people) spends about 2 ms of game code before drawing here, so about 8-10 ms on a mid phone, out of the 16.7 ms a smooth frame allows.
  • 11 changes are proposed, ranked by how much they help against how risky they are, built over about 3 turns by 4 builders and a reviewer, merged by the build master.

Pictures and memory

  • Draw calls (the 450 budget): the busiest is the junior common room zoomed out on a portrait phone at 433, then quiz night at 396. With shadows, the graphics chip gets 617 draws there.
  • Memory is steady: it comes back to the same numbers after visiting every deck and after a week of play.
  • Memory grows from 95 MB to 229 MB as you visit the decks, then stays there. Opening the game takes the same as in the last pass (about 100 MB); the extra 134 MB is kept for decks you've already left. It isn't a leak (it stops after one visit to each deck), but on a phone it's a lot to hold. Finding out exactly what holds it is the first job of item 3.

The checks

CHECKTABLE

The changes, ranked by gain against risk

Gain: big medium small   Risk: none low medium. Each item says how it is proven to change nothing you see or play. "Section" names the part of the game file it touches; its owner reviews it (plans/owners.md).

1Run only the checks a change affectschecks · test-speed seat
gain: bigrisk: none to the gamequestion 3

What: a small tool, tools/affected.py, reads which parts of the game a change touches and prints the checks to run. The map from parts to checks is made from real runs: each check is run once with the browser recording which of the game's functions it used (tried on 0.64.6 by TS1: it works). On top of that come the "run it whenever..." rules already written in DEV_NOTES. A change to something everything reads (the ship's clock, the save, the deck builder, the page itself) still runs every check.

Gain: today every turn runs its area's checks by hand, and the full round is about CHECKSUM of check time. A turn that touches one area would usually need 3-6 checks plus the quick check.

Why it's safe: it changes no game code and no check; it only chooses. It's tested by replaying recent merges from the build table: every check that actually failed on one of them must have been picked. The full round still runs at every release and at least once a day.

2The crowd sends only what changed to the graphics chipsection 8b · render seat
gain: big for checks, medium on phonesrisk: low

What: the crowd is drawn in groups of 12 people. When one person in a group changes (sits, stands, picks up a tray), today the game rewrites and re-sends everything from that person to the end of the group, and after skipped frames, everything changed since the last picture. The change keeps each person's shape in its own fixed place, so only that person's piece is re-sent.

Gain: in day_check, Deck 3's day drops from about 31 s towards 8-10 s (the uploads are 74% of it), and similar savings in every check that draws after skipping time. In play, the 4 MB single-frame uploads (a small stutter on a phone) become a few kilobytes.

Why it's safe: the same triangles in the same order, so the same picture. Proven by a probe that keeps a copy of everything sent to the graphics chip and compares it, byte for byte, with what the old code sends, at every drawn frame of a ship day on every deck; then cadet_test ALL IDENTICAL and 32 crowd shots after skipped frames (the test that caught the last bug of this kind, in 0.27.28).

3Find what fills the 228 MB of memorymeasure first · load seat
gain: up to ~130 MB less on a phonerisk: none to measure; each fix low

What we know: 95 MB right after opening; 229 MB once you've been to every deck, then flat. The growth is 81 MB of raw number arrays (the shape data of furniture and walls, kept on the game's side after it was sent to the graphics chip) and 40 MB of lists. What: follow who holds those arrays (a "retainers" walk of the memory snapshot), then a short list of the big ones that are waste (copies of decks you've left, shape data nobody reads again), each with its own small fix as a later turn.

Why it matters: phones have far less memory than a desktop; a game that holds less pauses less to tidy up, and the browser is less likely to reload the tab when you switch apps.

Why it's safe: measuring changes nothing. Each fix that follows is proven like item 5 (same results after a played day).

4Paint texture grain faster, same pixelssection 2 · load seat
gain: medium (about 0.5 s here, ~2 s on a phone)risk: low

What: the grain painter adds a random speck to every pixel of every texture, one by one. The same specks, in the same order, can be made with a much tighter loop (no change to the numbers drawn).

Why it's safe: a probe fingerprints every painted texture and the game's random-number position after opening; both must match the old build exactly. Then cadet_test ALL IDENTICAL.

5Lighter busy framessections 8b, 10, 14, 11, 15, 19 · frame seat
gain: medium (aim: a quarter off the 2 ms)risk: medium (many owners)

What: small, separate savings, one area at a time: remember the screen-size answers (matchMedia) and the HUD's button positions until the screen actually changes, instead of measuring every frame; ask "where should this person be now?" (whereIs, planWhere, walkGap) once per person per ship moment instead of several times a frame; trim the crowd's posing work.

Why it's safe: after 900 frames of Sunday dinner with zoom changes, every crew member's position, pose and goal, the save and the random-number position are compared with the old build: they must match exactly (the method used for 0.27.27). cadet_test ALL IDENTICAL, day_check's output line for line. Each owner reviews their area.

6Speed readout on your own phonesection 25 (Dev mode) · frame seat with the Dev mode owner
gain: real phone numbersrisk: none (hidden)question 4

What: our measurements come from a desktop drawing in software, so we guess at phone numbers. A small "Speed" card in Dev mode (only with the Dev link) would show, on your phone: how long opening took (each step), game code and drawing per frame, draw calls, and memory. 7Remember painted textures between visitssections 2, 4b · load seat
gain: medium (every open after the first)risk: mediumquestion 2

What: after the first open, keep the finished textures in the phone's browser storage, labelled with the build number and a fingerprint of the painting code. Later opens load them instead of painting (about 1 s here, several on a phone). It also stores where the random-number list stood after painting, so everything after it carries on exactly the same.

Why it's safe: the probe from item 4 compares a cached open with a painted one: same pixels, same random-number position. A cache with the wrong label is ignored and repainted. If storage is full or blocked, the game simply paints as now.

Risk: a wrongly labelled cache would show old textures; that's what the fingerprint guards against. Planned after items 1-5.

8Faster deck changessections 4b, 4c · render seat
gain: medium (Deck 3 builds in 1.1 s here, about 4-5 s on a phone)risk: low

What: building a deck merges thousands of furniture pieces into a few shapes; the merge first copies every piece into a slower form (toNonIndexed, 0.3 s of Deck 4's 1.3 s) and measures the hull edge by edge. Both can make exactly the same result with less copying. Measured already: building takes 0.1-0.4 s on Decks 1, 5, 6 and the rec deck, 0.7-0.9 s on Decks 2 and 4, 1.1 s on Deck 3 (plans/opt-measure.md). Turn 2 profiles Decks 3, 2 and 4 and works on their slowest parts.

Why it's safe: every merged shape is compared byte for byte with the old build's on all seven decks (the method used for the shadow stand-ins in 0.27.33); cadet_test ALL IDENTICAL; deck_check OK.

9Long checks that pick up where they stopped, and the full round shared outchecks · test-speed seat
gain: mediumrisk: none to the game

What: each long check writes a line per part as it goes (part, build fingerprint, OK or FAIL, seconds); a rerun on the same build skips the parts already passed. The full round is listed in one file, and several runner sessions each take a slice and report back, so one stuck runner never holds up the others.

Why it's safe: only parts that don't depend on what the part before left behind are skipped (DEV_NOTES lists the ones that do); results are compared with a whole run before it's relied on.

11Draw-call headroom in the junior common roomsection 4d · watch only
gain: safety marginrisk: lowquestion 7

At 433 of 450 when zoomed out, any new decor there breaks the budget. The proposal is to watch it (perf_check already does) and not touch it in this pass, unless you'd rather we free up room now by merging more of its still furniture (same picture, checked shot for shot).

Not proposed

  • Checks without drawing: your rule; every check still draws the real game.
  • Visible trade-offs (softer or blockier shadows on small screens, people far away moving less often, fewer decorations): each would change what you see. Only if you ask for it (question 6).
  • Test browsers keeping compiled shaders between runs: tried (a kept browser profile and Chrome's shader store): no measurable gain, the software renderer compiles them again anyway.
  • Fewer kinds of materials to compile fewer shaders: it would change colours and shine.
  • Cutting the dialogue file down: it's already stored in the fast form and takes under 0.1 s to read. Most hosts send the page compressed (1.6 MB instead of 5.5 MB); the lead checks that the playable link does.

How each change is proven to change nothing

  • Pictures: cadet_test against the build before, ALL IDENTICAL (the known one-level renderer noise excepted), plus the item's own extra shots.
  • The crew and the ship: day_check's output line for line, events_check, food_check and machine_check OK, and for frame changes a played Sunday dinner compared person by person.
  • The random numbers: the "random" list's position after opening and after a played hour is compared with the old build. Shared kit made at load still never draws from it.
  • Before and after numbers: one bench tool (tools/opt_bench.py, turn 0) measures opening, deck changes, busy frames, memory, uploads and each check's time; every turn adds its before/after row to plans/opt-measure.md.
  • Review: an adversarial reviewer re-runs the proof for every item before the build master merges it. The quick check passes before every push, as always.
