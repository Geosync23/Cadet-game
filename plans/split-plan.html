Plan page for the user's review (split architect SA1, checked and revised by the split reviewer SR1, 2026-10-20; the review: plans/split-plan-review.md). Nothing is cut until you sign this off. Based on the final rec deck build (0.64.2 today, branch claude/rec-cand-s1); the cut is made on whatever that build is when you sign it off.
In one breath.

Today the whole game is one file of about 49,800 lines that every helper edits at once, which is how yesterday's late name clash and the long hand merges happened. We cut it into 40 smaller files ("pieces") along the section lines the file already has: Deck 4, the galley, the device, the crew's schedules and so on. A tiny script then glues the pieces back, in order, into the same single starship-cadet.html you play today. Your link, the published game and every check keep working exactly as now.

The proof: the glued file is identical to today's file down to the last letter, so it is the same game and every test result still holds. We already tried this twice, on 0.64.0 and on 0.64.2, by two helpers working separately: both times it came back identical, and every piece can be checked on its own. And if the split ever turns out to be a bad idea, going back is easy (section 6).

Alongside the split we add the new ways of working you approved: who owns which piece, a quick check before every push, the same check run by GitHub on every push, and one shared branch everyone merges into early.

What you need to decide

1. The pieces and who owns them. The list below follows the file's own sections, so the cut is mechanical and nothing is rewritten. Happy with this list? (We can split big pieces further later, during the clean-up.)

2. Keep the glued game file in git? Recommended: yes. After each change the helper runs the glue script and saves both the piece and the glued file. Good: your link, the published game, every check, and "fetch an old version" all keep working with no change; anyone can grab the whole game in one file at any time. Cost: each change appears twice in the history (piece + glued file), and the glued file is never fixed by hand: the quick check refuses a glued file that doesn't match its pieces, and a small script puts them back in step the safe way (section 6). The other choice, gluing only when needed, saves that duplication but means every check, every publish and every helper must remember to glue first, and an old version can't be opened directly.

3. Automatic checks on GitHub on every push. Your repository is public (anyone with the link can read it), so GitHub runs these checks free, with no monthly limit. OK to switch it on? If you ever make the repository private: GitHub's free plan includes 2,000 minutes a month, which at our pace would last a day or two, so we would run the GitHub check only on the shared branch (about 9 runs a day fits). Helpers would still run the quick check themselves before every push. You would never get a surprise bill: GitHub's spending limit starts at $0, so the checks just pause until the next month.

Pieces live in a new pieces/ folder: pieces/page/ (the page around the game: its look and on-screen panels), pieces/js/ (the game code) and pieces/content/ (generated words). Each piece is named after the file section it holds (s19-device.js is section 19, as the code's own notes call it), and pieces/ORDER lists them in today's order exactly, which is why the result is identical. The owners table goes into plans/owners.md, with each piece's shared functions and their exact inputs (e.g. recShow(state)); a change in someone else's piece goes through its owner.

2. The glue script

build.py: well under 100 lines of python3, nothing to install (the checks already use python3). It reads the list of pieces in order from pieces/ORDER and joins them into starship-cadet.html. It takes a quarter of a second, and the same pieces always give the same file. python3 build.py --check only compares and says whether the game file is up to date, and if not, which pieces differ.

A second small script, split.py, does the cut itself, by finding the section headings (not line numbers, so it still works after the file changes). Run on a glued file it gives back exactly its pieces, which is how work that reached the glued file but not the pieces is carried over safely (see Risks).

Two writers' tools change one line each: content_gen.py writes the crew's words into pieces/content/words.gen.js instead of the game file (tested: it reads that piece unchanged and says "up to date"), and the crew roster generator writes into the crew data piece. Both refuse to write into starship-cadet.html from then on, so nobody's words are lost to the next glue.

Technical detail (for the team)

Where the cuts fall

Each cut is at a section header (// ==== line + numbered title) or a generated-block marker. The script's opening (() => { goes in page/body.html and the closing })(); in page/tail.html, so every .js piece is whole and passes node --check on its own (verified on all 36, on 0.64.0 and 0.64.2). Cuts are found by marker, never by line number: the script's opener is the first column-0 (() => { (there are 5) and the closer the last column-0 })(); (there are 17); the shared places piece starts at // ---- Big gatherings. Each marker must be found exactly once (in order), or split.py stops. The file's sections aren't in numeric order (6, 7, 8 come after 24); the pieces keep file order, not section numbers. The FILE MAP comment stays at the top of 01-setup-materials.js. Every piece ends with a newline (tail.html too: the file ends with </html> and a newline); joining is plain concatenation, no separators. build.py refuses a piece without its final newline: otherwise the piece's last line and the next piece's first line become one line, and a // note at the end of one would silently swallow the next piece's first line of code.

build.py (sketch)

order = [l for l in open('pieces/ORDER').read().split('\n') if l.strip()]
data = b''.join(open('pieces/' + n, 'rb').read() for n in order)
if '--check' in sys.argv: sys.exit(0 if open(GAME, 'rb').read() == data else 1)
open(GAME, 'wb').write(data)
# plus: every piece must end with b'\n'; --check names the pieces that differ
#       (split the game file in memory and compare piece by piece)

Getting back in step (the one rule that loses work if done wrong)

build.py --check fails in two different situations. (a) A piece changed and the glue was forgotten: run build.py. (b) A merge brought in changes to the glued file only (a branch from before the split, or a helper who edited the glued file by mistake): git merges starship-cadet.html cleanly and silently, the pieces don't change, and build.py would then overwrite that work. Run split.py on the glued file instead: it cuts the merged file back into pieces, keeping both sides. Tried on a copy of 0.64.2: an old-branch edit plus a newer piece edit; build.py lost the old-branch edit, split.py kept both. The scripts decide which case it is and say so, so nobody has to remember the rule: they compare against the commit before (for a merge, which git commits on its own, the shared branch's side of it, HEAD^1; for unsaved edits, HEAD): pieces changed and glued didn't, glue; glued changed and pieces didn't, cut; both changed and still out of step, stop and ask the build master.

Bytes in, bytes out: no line-ending or encoding handling, so it can't alter a letter. Trial: 0.25 s for split + join on 0.64.0 (5,129,461 bytes, sha256 534ceeda1449f7cb886b80b78ecffb75af257c7c177ac77889afad7319e918aa).

Duplicate-name scan

All game code runs inside one function, so a repeated const/let stops the game loading (the parse step catches it), and a repeated function silently replaces the first (the dangerous one). A column-0 text search misses names after the first in let W = 0, D = 0, … (3,359 found against 3,807 real) and every one-line Object.assign(PLAYER_ACTS, { … }). So the scan reads the glued script with a real JavaScript reader (acorn, fetched once with npm pack like three.js; the reviewer's sketch is plans/split-tools/names_check.js): every name declared at the top of the game function, and every key added to a shared table by const TABLE = {…} or Object.assign(TABLE, {…}). 0.64.2: 3,807 names, 2,740 table keys, no repeats, 1.1 s. It caught all three planted mistakes (a second function, a second PLAYER_ACTS.tidy, a second let). It reads the script as the browser does (a script, not a node module), so it also replaces node --check on the whole, which accepts things a browser refuses (a stray top-level return).
