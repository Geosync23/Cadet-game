Step 2: splitting the game into pieces

Plan page for the user's review (split architect, 2026-10-20). Nothing is cut until you sign this off. Based on the rec deck build 0.64.0 (branch claude/rec-cand-s1).
In one breath.

Today the whole game is one file of about 49,800 lines that every helper edits at once, which is how yesterday's late name clash and the long hand merges happened. We cut it into 39 smaller files ("pieces") along the section lines the file already has: Deck 4, the galley, the device, the crew's schedules and so on. A tiny script then glues the pieces back, in order, into the same single starship-cadet.html you play today. Your link, the published game and every check keep working exactly as now.

The proof: the glued file is identical to today's file down to the last letter, so it is the same game and every test result still holds. We already tried this on a copy of 0.64.0: it came back identical, and every piece can be checked on its own.

Alongside the split we add the new ways of working you approved: who owns which piece, a quick check before every push, the same check run by GitHub on every push, and one shared branch everyone merges into early.

What you need to decide

1. The pieces and who owns them. The list below follows the file's own sections, so the cut is mechanical and nothing is rewritten. Happy with this list? (We can split big pieces further later, during the clean-up.)

2. Keep the glued game file in git? Recommended: yes. After each change the helper runs the glue script and saves both the piece and the glued file. Good: your link, the published game, every check, and "fetch an old version" all keep working with no change; anyone can grab the whole game in one file at any time. Cost: each change appears twice in the history (piece + glued file), and when two helpers' work is combined the glued file is never fixed by hand, just rebuilt by the script (the quick check refuses a glued file that doesn't match its pieces). The other choice, gluing only when needed, saves that duplication but means every check, every publish and every helper must remember to glue first, and an old version can't be opened directly.

3. Automatic checks on GitHub on every push. Your repository is public (anyone with the link can read it), so GitHub runs these checks free, with no monthly limit. OK to switch it on? If you ever make the repository private, the free allowance (2,000 minutes a month) would last only a few days at our pace, and we'd limit it to the shared branch.

Pieces live in a new pieces/ folder: pieces/page/ (the page around the game: its look and on-screen panels), pieces/js/ (the game code, numbered in the order they're glued) and pieces/content/ (generated words). The numbers keep today's order exactly, which is why the result is identical. The owners table goes into plans/owners.md, with each piece's shared functions and their exact inputs (e.g. recShow(state)); a change in someone else's piece goes through its owner.

2. The glue script

build.py: about 30 lines of python3, nothing to install (the checks already use python3). It reads the list of pieces in order from pieces/ORDER and joins them into starship-cadet.html. It takes a quarter of a second, and the same pieces always give the same file. python3 build.py --check only compares and says whether the game file is up to date.

A second small script, split.py, does the cut itself, by finding the section headings. It can be run again on any old whole file, which is how a helper's unfinished work from before the split is carried over (see Risks).

Two writers' tools change one line each: content_gen.py writes the crew's words into pieces/content/words.gen.js instead of the game file (tested: it reads that piece unchanged and says "up to date"), and the crew roster generator writes into the crew data piece.

3. The proof, and keeping the whole file

  1. Keep the whole file first (your rule): when 0.64.0 is signed off, tag it in git as whole-file-0.64.0 and keep a copy at archive/starship-cadet-0.64.0-whole.html. The whole game can always be fetched in one piece from there.
  2. Cut, glue, and compare: the glued file must match 0.64.0 byte for byte. We show both files' fingerprints (a 64-letter code that changes if even one letter changes); they must be the same. Trial on 0.64.0 today: both 534ceeda…918aa.
  3. Because the file is identical, every check's last result carries over; we still run the quick check once on GitHub to prove the new set-up works. Nothing new to publish: the game hasn't changed.

5. One shared branch, merged into early

A new branch claude/integration starts from the split. Each helper works on its own branch, started from it. When a piece of work is reviewed, the build master merges it into claude/integration straight away (helpers can only push to their own branch), runs the glue and the quick check, and pushes. Helpers bring the shared branch into theirs often, so nobody drifts days apart. When you approve a milestone, it goes to main as today, with your OK.

Two new notes keep everyone oriented: plans/map.md ("where things live": which piece holds what, kept current by whoever moves code), and plans/backlog.md (small known bugs, so things found in passing aren't lost), started from the roadmap's list: the unclosed style comment near the top, the hidden door gear, the double clock hold in the evenings, two wall faults leaving you queued, rec talent night only skipping day 152, the Tracked panel filling small phones, and the "seven decks" Deck 4 texts not gated.

Technical detail (for the team)

Where the cuts fall

Each cut is at a section header (// ==== line + numbered title) or a generated-block marker. The script's opening (() => { goes in page/body.html and the closing })(); in page/tail.html, so every .js piece is whole and passes node --check on its own (verified on all 35). The file's sections aren't in numeric order (6, 7, 8 come after 24); the pieces keep file order, not section numbers. The FILE MAP comment stays at the top of 01-setup-materials.js. Each piece file ends with a newline except tail.html; joining is plain concatenation, no separators.

build.py (sketch)

order = [l for l in open('pieces/ORDER').read().split('\n') if l.strip()]
data = b''.join(open('pieces/' + n, 'rb').read() for n in order)
if '--check' in sys.argv: sys.exit(0 if open(GAME, 'rb').read() == data else 1)
open(GAME, 'wb').write(data)

Bytes in, bytes out: no line-ending or encoding handling, so it can't alter a letter. Trial: 0.25 s for split + join on 0.64.0 (5,129,461 bytes, sha256 534ceeda1449f7cb886b80b78ecffb75af257c7c177ac77889afad7319e918aa).

Duplicate-name scan

All game code runs inside one function, so a repeated const/let stops the game loading, and a repeated function silently replaces the first (the dangerous one). The scan lists names declared at column 0 (function, const, let, var, class) across all pieces and fails on any repeat, naming both pieces. 0.64.0: 3,359 names (1,538 functions, 1,659 const), no repeats. Names added by Object.assign(PLAYER_ACTS, …)-style merges aren't covered; a later step can add a key-clash scan for the shared tables.
